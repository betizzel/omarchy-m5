> For picking this up in a fresh session (Devin cloud or otherwise).

## Target machine (verified on-device)

- MacBook Pro 14" M5 Pro — **Mac17,9 / J714sAP**, SoC **T6050 "Sotra_S"**
- macOS Tahoe 26.5, 48 GB RAM, 1 TB SSD
- Binned SKU: **15 cores (5+5+5)** — cpu5/cpu11/cpu17 fused off
- Disk: `disk0s1` iSC, `disk0s2` macOS APFS container (994.6 GB, ~615 GB
  free), `disk0s3` Apple_APFS_Recovery. macOS VGID:
  `863345B8-7FEC-4FD2-996D-187D72EC9A66`

## What's done

- **Phase 0 research** — 4 reports in `docs/research/` (kernel/boot chain,
  hardware matrix, Omarchy ARM ecosystem, dual-boot mechanics).
- **Dev harness** — `Makefile` + `scripts/build-kernel.sh` +
  `scripts/host-shim/` (glibc headers macOS lacks). `make setup/fetch/
  m1n1/dtbs/kernel` all work on macOS; vendors `m1n1` main and
  `linux` asahi-wip-7.2 under `vendor/`.
- **Device trees populated from the real ADT** — extracted this machine's
  `devicetree.img4` (IM4P + LZFSE) and generated real values:
  - `dt/t6050-pmgr.dtsi` — generated by `scripts/adt2pmgr.py` (fixed fork
    of m1n1's `pmgr_adt2dt.py`; upstream crashes on T6050 die-level parent
    IDs 219/325/609 and no_ps parents). 405 power domains, 6 PMGR blocks.
  - `dt/t6050.dtsi` — real IRQs (uart0=1359, wdt=721, dockchannel=360,
    i2c0-4=1375-1379, spi2/4=1369/1371), npins (61/85/221), CPU
    compatibles (`apple,sawtooth` M-cores, `apple,everest` P-cores),
    power-domains wired to ps_* nodes.
  - `dt/t6050-j714s.dts` / `t6050-j716s.dts` — board files; j714s
    disables the 3 absent cores.
  - Both DTBs compile clean via `make dtbs` (86K each).
- **`scripts/prep-stub.sh`** — one-shot stub container creation, fully
  on-disk (no IPSW). Shrinks macOS container, makes the 2.5 GB Omarchy
  volume group, clones restore bundle + `arm64eBaseSystem.dmg` +
  `AdminUserRecoveryInfo.plist`, adds a 500 MB EFI partition, prints the
  VGID + exact bless/bputil/kmutil commands. **Untested end-to-end** —
  first real run is the test; it fails closed and never touches
  disk0s1/disk0s3.

## What's next (in order)

1. **Run `sudo scripts/prep-stub.sh`** on the M5 Pro (optionally
   `--linux-size 200G`). Verify the printed VGID and volume layout.
2. **Build m1n1** (`make m1n1`, `CHAINLOADING=0` for the installed
   image), copy `m1n1.bin` to the EFI partition.
3. **The 1TR ceremony** (manual, on-device): `bless --setBoot` →
   shutdown → power-hold into 1TR → pick "Omarchy" → in its recoveryOS
   Terminal: `bputil -d -v <vgid>` (must show `: Paired` + `one true
   recoveryOS`), `bputil -nc -v <vgid>`, `kmutil configure-boot -c
   m1n1.bin --raw --entry-point 2048 --lowest-virtual-address 0 -v
   <sysvol>`. Full steps in `docs/bringup.md`.
4. **Tethered dev loop**: chainload test m1n1/kernels over USB-C via
   `proxyclient/tools/chainload.py` / `linux.py`. First kernel boot:
   `maxcpus=1` + WFI workaround; console via dockchannel-UART or simplefb.

## Key risks / known blockers

- **SMP is broken on T6050** — secondaries never execute the reset
  vector. First milestone is single-core TTY (`maxcpus=1`).
- **prep-stub.sh is untested** — worst realistic failure is a
  not-paired recoveryOS (retryable); catastrophic case is DFU restore.
- **Upstream churn** — asahi-wip/dev trees move weekly; rebase often.
- ADT `reg` values sit `0x2_0000_0000` below MMIO on this SoC
  (uart0 ADT 0x305200000 → MMIO 0x505200000).
