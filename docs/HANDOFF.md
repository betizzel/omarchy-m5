## Phase 1 status — kernel reaches a userspace shell (single core)

**The hard part is behind us.** As of 2026-09-21 the machine boots
iBoot → m1n1 stage1 → framebuffer console (3024x1964, DARTs up) from a
signed custom boot object. Everything below is memory-only or repeatable.

Stub facts (re-installed 2026-10-09): VGID
`83F76F48-1DE4-4C8B-99C0-E9D48E59AF0D`, GPT entry 3; EFI is entry 4; the
Linux root is entry 5 = `nvme0n1p5` (20 GB, LBA 238066151 + 4882812).
macOS's `disk0sN` names do not track GPT entries (right after the install
the root was `disk0s7`). `nvram boot-volume` points at the stub, so an
unattended boot goes to m1n1; macOS is power-hold → picker → Macintosh HD,
still Full Security.

The first install (VGID `B931CA67-AA4F-465B-B80D-B24814488E27`, 256 GB
root) was deleted on 2026-10-09 to give macOS room for local AI models,
with the Arch root and its boot policy. The macOS half of the re-install
is done (`docs/HANDOFF-mac.md`); the ceremony check and provisioning of
the empty root are in `docs/HANDOFF-thinkpad.md`.

Why the first ceremony attempt failed, for the record: the stub had no
`.IAPhysicalMedia`, so iBoot booted it as a plain OS, found no
LocalPolicy, and the picker offered "reinstall". `prep-stub.sh` alone does
not produce a pickable install-media volume — `finish-install.sh` does
(app bundle + boot.bin + dslocal + APFS bootable fsctl + bless + the
media marker, in asahi-installer's order).

Tethered loop is live: Arch ThinkPad T14 over USB-C, `make tether` packs
`build/tether-bundle.tar.gz` (proxyclient + kernel/DT/initramfs + a
chainloadable m1n1 + udev rule + runners).

**LINUX BOOTS (2026-09-22).** The checkpoint markers came back
**red → green → blue → white**: the kernel entered `head.S`, enabled the
MMU, parsed our `dt/t6050.dtsi`, completed `paging_init()` and reached
`console_init()`. AIC (AICv3), the timers, memblock and the devicetree all
appeared to work on T6050 - wrongly: see "USERSPACE" below; the AIC never
probed, and the "console" failure was a kernel with no interrupts.

Ruled out by inspection along the way:

- AICv3 **is** supported in this tree (`irq-apple-aic.c`,
  `apple,t8122-aic3`) and our DT uses it.
- dockchannel exists only as a SoC/HID driver — there is no dockchannel
  earlycon — so without the debug cable the framebuffer is the *only*
  output channel. That is why markers, not another console attempt.
- The framebuffer node is a proper `/chosen` child, so
  `of_platform_default_populate_init()` creates the platform device; and
  the framebuffer (`0x10bd3110000`) sits *above* the usable-RAM window
  m1n1 reports (`..0x10bcaaf8000`), so there is no RAM/aperture conflict.
- `CONFIG_FRAMEBUFFER_CONSOLE_DEFERRED_TAKEOVER` is off.
  `..._DETECT_PRIMARY` cannot be turned off (`DRM_CLIENT_SELECTION`
  selects it, and `olddefconfig` restores it) but is harmless on arm64:
  without a PCI VGA primary, fbcon falls back to the first framebuffer.

Markers now cover the console chain itself (`patches/linux/0001-*.patch`,
`<asm/omarchy_fbmarker.h>` for the row map): CYAN on a successful
`simpledrm_probe()`, MAGENTA on `do_fbcon_takeover()` success, ORANGE
before `kernel_init` execs `/init`, plus two bands painted from
**userspace** by the initramfs `/init` via `/dev/mem` (allowed:
`STRICT_DEVMEM` permits it because the framebuffer is outside usable RAM).
Late markers use `ioremap()` rather than `early_ioremap()`, chosen at
runtime with `slab_is_available()`, because the early mapping is long gone
by then. m1n1's control band moved to rows 144..159 to stay clear.

Row map: 0-15 entry, 16-31 MMU, 32-47 paging, 48-63 console_init, 64-79
simpledrm, 80-95 fbcon, 96-111 pre-/init, 112-127 /init running, 128-143
/dev/fb0 or /dev/dri/card0 exists, 144-159 m1n1 control.

`./dump-fdt.sh` captures the **final patched FDT** (new m1n1 proxy op
`P_KBOOT_GET_DT`) without booting. It and the other proxy tools now fail
with a clear message instead of a traceback when `/dev/m1n1` is gone —
they must run *before* `boot-linux.sh`, since the USB gadget disappears at
handoff.

Triage (resolved by the phase-barrier image):

- Every phase through `pcie_init` prints "done"; the trap is inside
  `dapf_init_all`, right after
  `dapf: /arm-io/dart-aop base 0x2890fc000 window 0x4000, dapf-instance-0
  length 936`. `L2C_ERR_ADR` low 40 bits = `0x2890fc180` = base + 0x180 =
  **slice 6**, which is *inside* the window (18 slices × 0x40 = 0x480), so
  this is not an overflow. The hardware appears to expose fewer APF slices
  than the ADT describes; the on-disk ADT carries
  `allow-dram-apf-slices-0 = 0` for this DART and m1n1 ignores it.
- PCIe was never implicated: its "Error getting node" lines are just the
  last prints before an *asynchronous* SError (`ESR 0xbe000000`, `FAR 0`),
  which is reported at whatever PC is executing.
- **The on-disk ADT is not the runtime ADT.** `devicetree.img4` from the
  restore bundle decompresses to 835984 bytes, but `boot_args.devtree_size`
  is 737280 — iBoot patches the tree before handing it over. They disagree
  about this very DART (on disk, `dart-aop` has one reg and *no*
  `dapf-instance-0`). Analyze only `./dump-adt.sh` output from the target.

Current image: `patches/m1n1/0001-*.patch` skips `/arm-io/dart-aop` DAPF on
T6050, prints and barriers every slice it does program, and clamps slice
counts to the reg window.

**Second blocker, fixed in `dt/`: CPU affinities.** The log showed m1n1
disabling *every* CPU, including the boot core, because `kboot.c` keeps a
CPU node only when its `reg` equals `MPIDR_EL1 & 0xFFFFFF`. This J714s
reports `MPIDR_EL1 = 0x80040000` → affinity `0x40000`, but `dt/t6050.dtsi`
used the M1/M2 `cluster << 8 | core` layout starting at `0x0`, so Linux
would have been handed a DT with no usable CPU. All 18 cores now carry
`Aff2 = 0x4`. Only the boot core's value is measured; the cluster/core bits
are unverified until secondaries run, but m1n1 hard-fails loudly on a
mismatch for any *live* core.

**USERSPACE (2026-10-01).** Kernel → simpledrm → fbcon (penguin) →
`/init` → BusyBox `sh` prompt, single core, kernel log on the panel. Built
and driven entirely from the ThinkPad (`scripts/build-kernel.sh` now runs
on Linux; incremental rebuild ~40 s). What it took, in order:

1. **On-panel kernel log.** `earlycon=efifb` now works on this DT boot:
   patch 0001 fills `sysfb_primary_display` from the marker geometry
   before `parse_early_param()` and withdraws the EFI type at
   `arch_initcall` so sysfb/efifb stay out of simpledrm's way. Text starts
   at row 160 (Terminus 16x32). This is what turned every later blocker
   into a photo of a panic instead of a frozen logo.
2. **AIC event register.** `dt/t6050.dtsi`'s AIC had one `reg`; AICv2/v3
   need reg[1] (`aic-iack-offset` = 0x40000 → `0x280440000`). Without it
   `aic_of_ic_init()` WARNs and returns before installing any handler and
   arm64 `init_IRQ()` does not panic, so the kernel ran with no interrupts
   and hung at its first sleep - the "white band, nothing after" symptom.
3. **`VM_TMR_FIQ_ENA_EL2` is write-locked on T6050** (reads 0xf, every
   write UNDEFINED at EL2 - probed from the proxy). Patch 0002 adds an
   `apple,t6050-aic3` variant that skips the write in `aic_init_cpu()` and
   refuses to map the guest timer FIQs in hyp mode (KVM's timer then fails
   cleanly instead of storming).
4. **PMGR tree from the runtime ADT.** The old `t6050-pmgr.dtsi` came from
   the on-disk ADT (405 domains incl. absent memory channels); the runtime
   ADT has 301. `scripts/adt2pmgr.py` now also takes `--boot-state`
   (`dt/t6050-j714s-pmgr-boot-state.json`, a probe snapshot): ADT-critical
   domains that are off at handover are not marked always-on, and CPU-
   complex domains (`mcpu*/pcpu*/mcpm*/pcpm*`) are not described at all,
   as in Asahi's M-series trees - Linux's probe write made PMGR enforce
   "off" on the running boot core.
5. **No writes to domains already under auto-PM** (patch 0003): a store
   to e.g. `dispext0_cpu` while iBoot has it auto-gated never completes.
6. **genpd sync_state honours `pd_ignore_unused`** (patch 0004); powering
   off some unclaimed domain SErrors. Which one is still unknown, so
   `pd_ignore_unused clk_ignore_unused` are part of the default cmdline.

Probe tools used for 3-5 are `scripts/probes/` (shipped as `hv/` in the
tether bundle): `probe-timer.py`, `probe-aic.py`, `probe-pmgr.py
hv/t6050-pmgr.dtsi` (also emits the `--boot-state` snapshot) and
`probe-pmgr-writes.py hv/pmgr-probe.json`. They make guarded sysreg/MMIO
accesses with `dsb; isb` so SErrors land inside m1n1's exception guard. A
write that *hangs* (no SError) needs a long power-button hold;
`journalctl -k` showing a fresh `usb 7-1: new high-speed` is the proof the
M5 really rebooted.

Known noise after the prompt: `b2bd_*` (die-to-die link) domains fail to
reach 0xf when the driver core powers them up for their child domains'
probes; harmless deferred probes.

**HYPERVISOR (2026-10-01).** Linux runs as a guest of the m1n1 hypervisor
with its console - and the `/init` shell, interactively - on the
hypervisor's virtual UART, i.e. `/dev/m1n1-sec` on the ThinkPad
(`./chainload.sh`, `hv/vuart-log.py /dev/m1n1-sec hv/vuart.log &`,
`./boot-hv.sh`). What it took (patches/m1n1):

- 0002: T6050 locks `VM_TMR_FIQ_ENA_EL2`, the gate the hypervisor uses to
  hold a guest timer's FIQ while the guest services its vFIQ. `hv_init()`
  detects the lock (guarded write-back of the register's own value) and
  `hv_update_fiq()` then masks a firing guest timer through its own IMASK;
  the ECV-trapped guest `CNT[PV]_CTL_EL0` accesses hide that IMASK.
- 0001: kboot reads the M4+/M5 `CTRR_M4_*_EL2` registers only at EL2 - as
  an EL1 guest they are UNDEFINED and the guest m1n1 died there.
- 0003: `wcslen()` in m1n1's freestanding libc. Current Rust/LLVM turns a
  loop in the Rust ADT code into a `wcslen` call (any toolchain since at
  least 1.98).

m1n1 now builds on the ThinkPad too (`scripts/build-m1n1.sh`: distro
cross gcc + a per-user rustup with `aarch64-unknown-none-softfloat`).

**SMP (2026-10-01): parked.** Secondary start on T6050 is unsolved
upstream too (m1n1 PR #610: "the cores turn on ... but never start
executing our code"; same on an M5 Max). Measured here with a read-only
probe and one diagnostic start attempt (`scripts/probes/t6050-smp-probe.py`;
raw output in `docs/research/probe-logs/t6050-smp-*`):

- all 15 RVBARs are locked by iBoot to m1n1's base page (correct);
- the PMGR core-alive word (`0x280688004`) is one bit per ADT cpu-id
  (`0x3fffe` at rest), not m1n1's `4*cluster+core`;
- on start, each core's `cpu-impl-reg+0x100` status changes within
  microseconds (`...d800` -> `...caef20d102` / `...4aef205102`), but no core
  ever checks in;
- the secondary-only CTRR "SMP-RO" window (`s3_0_c11_c0_{0,1}`,
  `[0x10005fb0000, 0x10005fbb000)`) is iBoot's WFI parking sled and lies
  inside m1n1's heap range;
- AIC3 `SW_SET` does not read back, so it is no breadcrumb channel.

The DT now carries the P-cluster MPIDRs `0x10200+` (Aff2 = core type: P 1,
M 4). Linux stays at `maxcpus=1`; m1n1 prunes non-alive cores from the FDT
anyway.

**SMP (2026-10-09): released cores execute nothing we can see.** All on the
installed stage-1 (no chainload), with `hv/wdt-arm.py` as the safety net:

- `hv/smp-start.py`: m1n1's own `smp_start_secondaries()` fails for all 14
  even though its heap (and the pre-#682 secondary stacks) starts above the
  CTRR_C window. Chainload/heap overlap is real (fixed: m1n1 patch 0004) but
  not the cause.
- `hv/smp-reset-crumb.py`: vector slot 0 at the locked RVBAR (written with
  m1n1's MMU off) replaced by a stack-free stub storing MPIDR to DRAM.
  Released M (cl 0, cl 1) and P (cl 2) cores leave no crumb.
- `hv/smp-sled-crumb.py`: the CTRR_C window is exactly
  `[top_of_kernel_data - 48K, top_of_kernel_data)` and holds 12288 `wfi`
  (the whole window). Turned into a `bl` sled into a crumb stub: no crumb
  either, with or without a fast IPI (`IPI_RR_LOCAL/GLOBAL`) to wake WFI.
- `hv/smp-release-try.py`: CPU_START `+0x0` mirrors `+0x4` (both `0x3fffe`
  at rest; release clears the core's bit in both); the PMGR device goes
  `0x100 -> 0x1f0`; status low byte `0x02` like the boot core, but bits
  15:14 and 39:38 set (cluster 0) or 14 and 38 (clusters 1/2) where the boot
  core has bit 37.
- The boot core's architectural `RVBAR_EL2` reads `0x1fc08c000` (iBoot's
  relocation target, as Sowyu/m5-azahi noted), not m1n1's base; that memory
  hangs the bus even with the MMU off.
- Bus hangs (no SError, watchdog reset needed): the ARM debug block's
  `EDPCSRhi` (`coresight+0x20000+0xac`), `cpu-impl-reg+0..0x200` scans,
  and read *or* write of `cpm-impl-reg+0x40f8` (macOS restoreACC's
  `0xe440f8`, m1n1 cpufreq's `+0x440f8` on M1-M3). `EDPCSRlo` and the
  `cpu-uttdbg-reg+0x90` PC sample read 0: no external debug on this part.

- `hv/smp-release-try.py plain cpuN --wdt`: both traps start by arming the
  watchdog for a reset 3 s (RVBAR) or 8 s (sled) later, an MMIO side
  effect that needs no DRAM coherency. No reset followed: the cores do not
  execute even those first instructions.
- iBoot (mBoot-18000.120.36, `iBoot.j714s.RELEASE`, link base
  `0x100c1aa4000`) builds the sled itself: it allocates 0xc000 (raw-image
  path) or 0x4000 bytes from kernel data, fills them with `0xd503207f` and
  keeps the address in a global (`+0x45e080`). The boot core's
  `RVBAR_EL2` `0x1fc08c000` is LLB's link base (SRAM).

So the release powers the core up, and it then runs somewhere that is
neither its locked RVBAR nor the sled - most likely iBoot's secure reset
path (`RVBAR_EL2`). Next: reverse iBoot/mBoot's reset handler for
secondaries (J714s 26.5 IPSW), and the SPTM-era handoff it expects.

**USB gadget networking (2026-10-01): works (CDC EEM).** The three DWC3 cores
run in peripheral mode with no PHY driver, on the eUSB2 PHY m1n1 left
running. What it took:
- leave the `ps_atc*` PMGR domains disabled in DT (probing them armed
  auto-PM, and the DWC3 soft reset then timed out);
- no USB2 LPM, no SUSPHY/ENBLSLPM (`snps,*` quirks);
- **no interrupt endpoints**. With NCM+ACM, the dwc3 trace showed
  SET_CONFIGURATION processed and ep0's status stage armed right after NCM
  queued its first notification on its interrupt IN endpoint. After that
  the controller raised no further events, GSTS showed no bus error, and the
  host timed out (-110). m1n1 never transmits on interrupt endpoints, and
  Apple's ADT has `ncm-interrupt-ep-disabled = 1` on this port. So the
  gadget is EEM only: Ethernet over two bulk endpoints, `cdc_eem` on the
  host.

The ThinkPad side is `sudo scripts/host-usbnet.sh`, run once per ThinkPad
boot. It permanently stops NetworkManager from managing `cdc_eem`
interfaces (otherwise NM fails DHCP after 45 s and strips every address,
link-local included) and installs a udev rule that gives each gadget
netdev `10.55.<n>.1`, so M5 reboots need no re-run. Each run also enables
forwarding, masquerades 10.55/16 on any egress (VPNs like proton0 route
forwarded traffic too), and adds the docker FORWARD accepts. Before the
first run, the M5 is reachable at `fe80::4d:35ff:fe00:2%<iface>`. dwc3
tracing stays on from boot (`/sys/kernel/tracing/trace`).

  (`mke2fs -d tarball`, no root), without linux-aarch64 and linux-firmware.
  It ships in `boot/initramfs-provision.cpio`. `provision-rootfs 163592953

- The boot cmdline adds `nvme_apple.flush_interval=0

- `ssh root@10.55.0.2` or `ssh bay@10.55.0.2` with the host key. The bring-up
  defaults are root/root on tty1 and passwordless sudo for wheel
  (`/etc/sudoers.d/10-wheel-bringup`); tighten both.
- Through the NAT: pacman (full -Syu), NTP, DNS. Until a kernel with

- Trackpad: the IPSW-extracted firmware loads (`Touch MT ready`), and swipes

- Claude Code 2.1.287 (native installer) runs as user `bay`, and

**CPU DVFS (2026-10-02).** The boot cluster (cluster 0, M,
`apple,sawtooth`) comes up at 2.65 GHz, iBoot's p-state 6, because neither
m1n1 nor Linux knew T6050 cpufreq. Its DVFS block is at `cpm-impl-reg -
0x40000` = 0x210e00000, with CMD at +0x20020 and STATUS at +0x20050 (T8112
layout). Live writes measured with `tools/cpuhz.c`: p-state N = pmgr
`voltage-states22-sram` entry N-2, 6 -> 2649 MHz, 7 -> 2961, 12 -> 4041,
15 -> 4303. 16 (4380) is refused. `scripts/gen-cpufreq-dt.py` writes
`dt/t6050-cpufreq.dtsi` (M clusters only; the P cluster's offset is
unverified), and `CONFIG_ARM_APPLE_SOC_CPUFREQ=y` runs it with the stock
t8112 path. Verified on hardware: `apple-cpufreq` with
`schedutil` scales 1.344-4.308 GHz (60% idle at 1344, 4308 MHz under load). `tools/devmem.c` peeks and pokes MMIO
via mmap (`/dev/mem` read() is RAM-only on arm64).

**Remote reboot (2026-10-02).** `CONFIG_APPLE_WATCHDOG=y`: `sudo systemctl
reboot` resets the M5 into stage-1 m1n1 within about 15 s, with no power
button. `~/tether/boot-m5.sh` (from `mktether.sh`) then runs the whole
cycle: wait for `/dev/m1n1`, chainload, `hv/nvme-proxy-probe.py`,
`boot-linux.sh` (SSD root by default), and wait for SSH. The ThinkPad's
udev rule addresses the gadget automatically.

**SMC (2026-10-02): stage 0 done, nothing enabled yet.** The plan and
draft DT are in `build/smc-draft/` (PLAN.md), from a research pass over the
ADT and the Asahi drivers. `hv/smc-proxy-probe.py` started the SMC endpoint
from m1n1 read-only. shmem is 0x28de84000 (inside the ADT nub region),
there are 3485 keys (catalogue: `docs/research/smc-keys-j714s.json`), and
CLKM, MSLD, bHLD, B0AV (13.0 V > BITV 9.0 V), BCF0=0, CHIS, AC-W, MBSE,

`scripts/qemu-rootfs.sh` boots the same kernel config (FB markers off),

## Key risks / known blockers

- **SMP is broken on T6050** — secondaries never execute the reset
  vector. m1n1 gives each core 100 ms and prints `Failed!` (~1.4 s total,
  not fatal). First milestone is single-core TTY (`maxcpus=1`).
- ~~prep-stub.sh is untested~~ — both it and `finish-install.sh` have now
  run end to end on the real machine; the ceremony completed.
- **m1n1 must be built with GNU Make >= 4.3** (`gmake`). macOS's 3.81
  mis-parses the Makefile's grouped targets (`&:`) into a target named
  `&`, which breaks `build_cfg.h` regeneration. `build-m1n1.sh` now
  enforces this.
- **`CHAINLOADING=` changes need `build_cfg.h` removed** — that rule has
  no prerequisites, so make considers the header up to date forever and
  silently rebuilds the *previous* config. `build-m1n1.sh` diffs the
  wanted config and deletes the header when it changes.
- **vendor/ is gitignored** — every upstream change MUST be captured in
  `patches/<tree>/` via `scripts/apply-patches.sh --refresh`, or it is lost
  on the next `make fetch`.
- **Upstream churn** — asahi-wip/dev trees move weekly; rebase often. The
  patches are against linux `236788cd2602` and m1n1 `4184923`, but
  `fetch-sources.sh` still follows branches, not those commits.
- ADT `reg` values sit `0x2_0000_0000` below MMIO on this SoC
  (uart0 ADT 0x305200000 → MMIO 0x505200000).
